# Kernel

Mizu is an operating system for autonomous model roles. This document is the
normative specification of what the kernel provides. Everything not described
here is deployment policy: it lives in the deployment's configuration and
policy files, and the kernel neither knows nor enforces it.

## What the kernel is and is not

| Part | Provides | Never decides |
|---|---|---|
| Units | Start, stop, interrupt and resume a unit of model work for a configured role; engine drivers, sessions, resource bounds, sandboxed execution, isolation, tool grants; content-addressed workspace snapshots | Which role exists, what it should do, what a good result is |
| Scheduler | Execution slots, the admission queue, cache-aware placement; wakes a role only when a message arrives in a queue it is woken by, or when a delayed message becomes due | Priorities between kinds of work, what counts as progress |
| Queues | Named, declared message queues: authenticated append, durable per-reader delivery facts, delayed delivery, references between messages | What a queue is for, what a message means, what any message "closes" or "completes" |
| Accounting | Request budgets, token usage, time | Spending policy |
| Drivers | Opaque operations on external systems (version control, CI, search, dependency materialisation); what they observe arrives as messages in a configured queue | Forge, CI, branch or review semantics |
| Tools | Model-facing operations over the parts above | How a model should behave |

Rules for kernel code:

- No role, purpose, queue name, message kind, state, lifecycle, branch name or
  workflow appears in kernel code. Proposals, decisions, questions, answers,
  notices, work items, reviews, audits and completion are all deployment
  policy: queues the deployment declares, and the role policy text that says
  what to do with their messages.
- The kernel has no notion of a record's state. Nothing is "open", "accepted",
  "answered" or "done" to the kernel. A message is appended, delivered and
  delivered; anything more is a reading of messages that roles, the
  dashboard or operator tooling make.
- Documented defaults for mechanism parameters are fine; example
  configurations ship under `examples/`.
- The kernel enforces integrity only: authentication of the author,
  append-only history, fail-closed validation of declared message schemas,
  bounded reads and writes, isolation, grants, budgets, and the single holder
  of a writable workspace (a resource property, not a role type).
- Model-facing text states facts: which tools exist, what each does, what an
  outcome causes. Instructions about behaviour belong to role policy files.
- The kernel does no work on a fixed cadence. A daemon sleeps until a message
  arrives in a queue that wakes it or the earliest delayed message becomes
  due. External systems that cannot notify the host are observed by a driver;
  the cost of an unchanged observation is one bounded driver call.

## Queues

A queue is declared by the deployment:

```toml
[queues.proposals]
write = ["role:*", "host", "operator"]   # principals that may append
read = ["role:writer", "operator"]       # principals that may read
wake = ["role:writer"]                   # readers woken by a new message (subset of read)
retain_days = 30                         # default 30; see Retention
# retain_last = 1                        # keep only newest N (not with wake or retain_days)
[queues.proposals.schema]                # optional; without it the body is any bounded JSON object
title = {type = "string", max = 200, required = true}
body = {type = "string", max = 65536}
```

- Principals: `role:<name>` (an authenticated unit of that role), `role:*`
  (any role), `host` (host components acting through the host: the check
  runner, drivers, operator tooling), `operator` (an operator-authenticated CLI
  call). The kernel binds the author; a message never names its own author.
- Schema field types: `string` (`max`, optional `values`), `integer`
  (`min`/`max`), `boolean`, `instant` (aware ISO time), `digest` (64 lowercase
  hex), `id` (a message id), `principal`, and `list` of one of these
  (`max_items`). `required` fields must be present. Unknown keys, unknown
  types and options that do not apply to a type refuse the configuration.

### Messages

```json
{"queue": "<name>", "seq": 41, "id": "<32 hex>", "author": "<principal>",
 "at": "<instant>", "deliver_at": "<instant or null>", "refs": ["<id>", ...],
 "body": {...}}
```

- A message is immutable and stored create-only. `seq` is gap-free per queue.
  `id` is generated by the kernel, or supplied by the writer for idempotent
  retries: a supplied id that already exists with the same author and content
  returns the existing message, and with different content is refused.
  A supplied id stays refused after its message is removed, so a retry cannot
  recreate it. A generated id is not a durable identity: its index entry
  retires with the message, and supplying that id later starts a new one.
  Writers needing a stable key across retention must supply their own id.
- `refs` lists ids of earlier messages in any queue the author may read. The
  kernel records them and offers lookup in both directions; it attaches no
  meaning to a reference. An answer, a decision, a revision or a withdrawal is
  simply a later message that refers to an earlier one, in whatever queue the
  deployment declares for it. References make threads: a message that refers
  to another wakes that message's author (when the author is a role that may
  read the reply), whatever the queue's `wake` list says, and is delivered with
  the messages it refers to that its reader may read. A question needs no
  waking queue for its answer to reach whoever asked.
- `deliver_at` delays delivery: the message is stored at once but is neither
  delivered nor wakes anyone before that instant. Delayed messages are the only
  timers: a deferral, a revisit or a deadline is a message to oneself or to
  another role with a delivery time. A delayed revisit is a hint, not
  authority: deployment consumers recheck the current decision chain with
  `message_refs` and may read a stale revisit without acting. The kernel
  has no withdraw or cancel, so a pending revisit still wakes its readers when
  due and blocks a contiguous read until then.

### Delivery

- Each reader principal has one create-only delivery fact per delivered
  message, stored beside that message. A read delivers the oldest messages in
  `seq` order that are due and have no fact for that reader, bounded per page.
  `next` never crosses a message that is not due yet: delivery is a contiguous
  run from the retained prefix, so a delayed message blocks later messages for
  that reader. A read stopped at one reports `delayed: true`, `next` at the last
  delivered message and `more: true`; wake on the message's due time to resume.
  `cursor` is only a page position through history: it chooses where a read
  starts, and the rows any read returns are recorded delivered, cursor or
  not. Messages already removed by retention leave a gap that reads cross.
- Appending a due message, or a delayed message becoming due, touches
  `wake/<role>` for each role in the queue's `wake` list. A queue wakes while it
  holds a due, wake-eligible message with no delivery fact for that reader;
  delivery consumes the wake. A dispatched unit records delivery for exactly
  the queue messages its serialized opening showed; a role whose prompt omits
  the optional `queues` section is handed no queue content, is not woken by
  queues, and credits nothing, so a shown message wakes once and an unshown
  one stays pending. A reader is not woken
  by its own message, except a delayed one, which is a wake its author asked
  for. A reply also wakes the author of the message it refers to (see `refs`).
  The service manager watches the wake files (systemd PathChanged, launchd
  WatchPaths, or the resident daemon's own watch). The scheduler sleeps until
  the next wake or the earliest `deliver_at`.
- Older `cursors/` and `woken/` files are converted to delivery facts once on
  first use and marked as migrated; afterwards delivery facts are the only
  reader state.

### Retention

A message is removed once every concrete reader in `read` has a delivery fact
for it, `retain_days` have passed, and no retained message refers to it. A
`role:*` grant names no concrete reader and fails closed: it never makes a
message removable on its own. Delivery facts go with their messages, so
removal deletes them too. Removal is done by the kernel when it next appends
to or reads that queue; it never runs on a timer of its own. Retention is
per-queue configuration with the default above; there is no total cap.

A queue may instead declare `retain_last = N` (1..64) for writer-owned count
retention: only the newest N messages are kept, regardless of delivery facts.
This mode excludes both `wake` (removal must not drop a wake edge) and
`retain_days`, and refuses messages with refs or delayed delivery that would pin
older history. A message another queue refers to is kept for id-addressable
reads, but it does not hold the prefix back: removal advances past it so the
queue stays bounded and readers see the newest facts. Such a message is
removed when its last referrer goes away. Removal is bounded per append or
read and advances the retained prefix, so later scans skip the holes.

## Host writers

Host components write through the same append operation, into queues the
deployment names in their configuration:

- the check runner writes each finished check's result (command, snapshot,
  status, evidence digests);
- each driver writes what it observes (for example CI results or a changed
  remote ref);
- operator tooling and the dashboard write operator messages.

None of these queue names, and no message vocabulary, is known to the kernel.

## Ready work

The host's ready-work page is a role-scoped reading of recorded work, not a
queue of intentions. An open item is ready while the named role has a free
doing slot; a held doing item stays actionable, and an item carrying a
registered wait re-enters the page only when recorded evidence makes that wait
due, impossible, absent or terminal. Pending, unknown and receipt-bound waits
stay held. Capacity and pending-wait counts are display facts; the change
fingerprint tracks ready-set membership alone. Admission and the finish probe
read the same page, so a role with nothing actionable has no ready work to
report.

## Finishing a unit

A unit ends with `finish`. The outcomes a role may use and their effects are
declared per role:

```toml
[roles.writer.outcomes]
continue = {readmit = true}
wait = {readmit = false}
```

- `readmit = true` asks the scheduler to admit the role again as soon as a
  slot is free. Otherwise the role sleeps until a message wakes it.
- A unit that is re-admitted on unchanged input and makes no progress is a
  no-progress unit whatever outcome it chose; the configured no-progress
  allowance, fresh-session recovery and parking apply.
- The kernel attaches no other meaning to an outcome name.

## Tools

| Tool | Effect |
|---|---|
| `queue_write(queue, body, refs?, deliver_at?, id?)` | Append a message if the role may write to the queue |
| `queue_read(queue, cursor?, limit?)` | Read the oldest due messages undelivered to the role, bounded, recording delivery; `cursor` only sets the page start (returned rows are still delivered); returns `next`, `head`, `more`, `delayed` |
| `message_read(id)` | Read one message the role may read |
| `message_refs(id, direction)` | List messages the role may read that refer to `id`, or that `id` refers to, bounded and paged |

Grants: the `queues` capability in the role's capability list, and the
per-queue `write` and `read` principals. No role holds either by default. The
host binds the acting principal; tools carry no actor or role argument. Pages
default to 64 messages and are capped at 512.

## Drivers

A driver is an operator-configured command speaking a JSON request/response
protocol. The kernel passes requests and returns responses without
interpreting provider concepts. A driver that observes an external system
returns observations, which the kernel appends to the driver's configured
queue. Version control, CI, pull requests, publication and review are driver
operations plus deployment policy; none of them is a kernel concept. The
development deployment projects its fixed `ci_head_state` rows and its opt-in
`ci_summary` aggregates this way: the trusted host gathers bounded raw
evidence, the declared driver owns the projection, and the caller validates
the returned facts. Wake and admission decisions never read those observations.

### Declaration

Each driver is a `[drivers.<name>]` table; a name is a lowercase identifier,
as queue names are. An absent or empty `[drivers]` table is valid and changes
nothing. All declarations are validated together: one bad declaration refuses
the whole configuration with a `ConfigError`.

| Key | Meaning | Default | Bound |
|---|---|---|---|
| `command` | argv array of the operator-owned program | required | nonempty array of nonempty strings without newline or NUL |
| `timeout_seconds` | wall deadline of one call | `20` | finite number in [1, 86400] |
| `max_bytes` | canonical request and combined output byte cap | `524288` | integer in [1024, 16777216] |
| `observation_queue` | queue that receives observations | required | a declared queue whose `write` principals include `host` |
| `diagnostic_bytes` | stderr tail attached to a nonzero-exit failure | `0` (disabled) | integer in [0, 8192] |

### Protocol and records

`invoke(driver, request, cancel=...)` takes one dict request, serializes it
canonically with `fs.canonical`, refuses NUL and a canonical request longer
than `max_bytes`, then runs `command` once with that request on stdin. The
program must print one JSON object on stdout. Any JSON object is a valid
response; the kernel returns it verbatim as an external-untrusted dict and
assigns no meaning to its keys. An observing driver returns an `observations`
key holding a list of at most 1024 plain objects. `record_observations(store,
driver, response)` appends each object to the declared queue as `host` and
returns only `{"appended": n}`. Observation bodies stay opaque: the queue's own
declared schema and its 1 MiB body bound still apply, so a body the queue
refuses fails closed. Appends are sequential, not transactional: a refusal
raises `Denied` after any earlier appends remain in the queue.

### Trust, retry, evidence and failure

The command is operator configuration, never model-provided argv, and never
runs in the sandbox. Requests, responses and the bounded stderr tail attached
to a nonzero-exit failure are external-untrusted; the tail is labelled as
such. Each call invokes the program once under `timeout_seconds`, polling an
optional `cancel` callback; there is no shell retry and no automatic
replay after cancellation. The returned dict and the append receipt carry no
provider meaning: callers bind them to their own records and digests, and the
kernel records no driver-specific evidence.

Failures are fail-closed `Denied`: a non-dict request, NUL or oversize
request, timeout, output-limit, cancellation, any nonzero exit or reason other
than a clean exit, and malformed, duplicate-key, non-finite, over-deep or
non-object JSON on stdout. `record_observations` refuses a non-dict response,
a missing, non-list or over-long `observations` value, a non-object body, and
any append the destination queue's schema or grants reject.

## Bounds

Bounds are either fixed mechanism limits or configuration with documented
defaults: message and field sizes, page sizes, retention. Reads are bounded
per response, never in total reachability. Current mechanism defaults are a
1 MiB message body and pages of 64 messages capped at 512.
